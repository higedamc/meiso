# ローカルリレー（Citrine 等）と楽観的UIの扱い

## 現状の整理

### リレーの扱い

- リレーは **フラットなリスト**（AppSettings.relays / Kind 10002）で、**区別なし**で扱われている。
- **接続**: Rust の `initNostrClient` / `initNostrClientWithPubkey` で渡したリレーを **すべて** `add_relay` し、同じ重みで接続。
- **読み取り**: REQ は接続済みリレー全体に送られ、返ってきたイベントを集約（例: 同じ d-tag なら created_at 最新 or 最古を採用）。「ローカルだけ先に読む」といった優先順位はない。
- **書き込み**: `send_event` は **全リレーに一括送信**。特定リレーだけ先に書く／あとから他に送る、といった段階はない。
- **ローカル保存**: 端末上のキャッシュは **Hive**（todos box）。「ローカルリレーにキャッシュする」という層はなく、Nostr の読み書きはすべて「リレー群」に対して行っている。

### Citrine 等のローカルリレーを追加した場合

- 設定画面で `wss://localhost:7777` や `wss://192.168.x.x:7777` などをリレーとして追加すれば、**他のリレーと同様に**読み書きの対象になる。
- オフライン時:
  - **ローカルリレーだけ**を設定していて、かつ Citrine が動いていれば、そのリレー経由で読み書き可能。
  - グローバルリレーも並列で入っている場合は、ローカルだけ落ちていても他リレーで動く（逆に、グローバルが落ちていてローカルのみの場合はローカルだけ使われる）。
- 「ローカルリレーを優先してキャッシュする」という**特別な処理は現状ない**。あくまで「そのリレーがリストに含まれているかどうか」だけ。

---

## 望ましい挙動（要望の整理）

1. **ローカルリレーを優先してキャッシュ**
   - オフラインでもオンラインでも、まずローカルリレーを「自分のデータの置き場」として使いたい。
2. **楽観的UI ＋ ローカルリレー**
   - 操作は即座に UI に反映（楽観的更新）。
   - 書き込みは **ローカルリレーに先に送り**、その結果で UI を確定（または確定に近づける）。
3. **バックグラウンドでグローバル同期**
   - ローカルリレーへの書き込みのあと、**バックグラウンドで**グローバルリレーへ同じイベントを送り、少しずつ同期する。

---

## 実装前の壁打ち・設計の方向性

### 1. リレーを「ローカル」と「グローバル」に分ける

- **案 A: 設定で種別を付ける**
  - 例: リレーリストに `{ url, role: "local" | "global" }` を持たせる。
  - 「ローカル」に 1 本（Citrine）、「グローバル」に複数、のようにする。
- **案 B: URL で推測する**
  - 例: `localhost` / `127.0.0.1` / `192.168.x.x` / `10.x.x.x` ならローカルとみなす。実装は簡単だが、ユーザーが別の URL でローカルリレーを立てていると拾えない。
- **案 C: 順序で決める**
  - 例: リストの先頭 1 本を「優先（ローカル想定）」、残りをグローバル。UI で並べ替え可能にすると、「ローカルを一番上に」で運用できる。

「ローカル 1 本 ＋ グローバル複数」をはっきり決めたいなら **案 A** が扱いやすい。

### 2. 書き込みの流れ（ローカル優先 → バックグラウンドでグローバル）

- **現在**: 1 イベントを全リレーに同時送信。
- **変更案**:
  1. **楽観的UI**: 従来どおり、操作した時点でローカル状態（＋必要なら Hive）を更新し、UI に即反映。
  2. **送信**: まず **ローカルリレーだけ** に `send_event`（または「ローカルと判定したリレー」のみに送る API を Rust 側に用意）。
  3. **成功したら**: その時点で「ローカルには載った」とみなしてよい。必要なら「未グローバル同期」フラグを付ける。
  4. **バックグラウンド**: 同じイベントを **グローバルリレー** に非同期で送信。失敗したらリトライ／キューに積む。

これには **Rust 側の変更** がいる:
- 今の `send_event` は「全リレーに一括」。  
  「特定リレーだけに送る」「あとから別のリレー群に送る」をやるには、  
  - リレーを「ローカル用」と「グローバル用」に分けて保持する、  
  - または「送信先リレーリスト」を引数で渡す、  
  などの API 拡張が必要。

### 3. 読み取りの流れ（ローカル優先の「見た目」）

- **現在**: 全リレーに REQ を飛ばし、返ってきたイベントをマージ。
- **変更案**:
  - **ファーストペイント**: ローカルリレー（＋既存の Hive キャッシュ）から先に読んで UI を出す。体感が速くなる。
  - **その後**: グローバルリレーからも取得し、同じ d-tag なら「より新しい方を採用」などでマージし、必要ならローカルリレーや Hive を更新。

ローカルだけ読む API が Rust にない場合は、「ローカルリレーだけを接続したクライアント」で一度 REQ する、あるいは「リレーを 2 グループに分けて、先にローカルグループにだけ REQ する」などの拡張が必要。

### 4. オフライン・オンラインの切り替え

- **オフライン**: ローカルリレー（Citrine）＋ Hive があれば、今の「ローカルストレージ優先」の流れを活かしつつ、**読み書き先をローカルリレーに限定**すればよい。
- **オンライン復帰時**: バックグラウンドで「ローカルにしかないイベントをグローバルに送る」「グローバルから最新を取ってマージする」の両方をやると、意図に近い。

### 5. まとめ（実装のステップ案）

- **Phase 0（現状）**: Citrine をリレーに追加すれば、他リレーと同様に読み書きされる。特別な「ローカル優先」はなし。
- **Phase 1**: リレーを「ローカル」「グローバル」と区別する設定を導入（UI で種別を選べる or 並び順で先頭をローカルとみなす）。
- **Phase 2**: 書き込みを「ローカルに先に送信 → 成功したら楽観的UIを確定 → バックグラウンドでグローバルに送信」に変更（Rust の send 先を分ける API が必要）。
- **Phase 3**: 読み取りを「ローカル（＋Hive）を先に表示 → 後からグローバルでマージ」に変更（Rust でリレーグループ別の REQ か、接続順の制御が必要）。

「ローカルリレーに優先的にキャッシュし、オフラインでもオンラインでも使えるようにする」＋「楽観的UI はローカルリレーで完結し、バックグラウンドでグローバルへ同期」は、上記のようにリレー種別と送信/購読の順序を分ける設計にすると実現しやすい。
